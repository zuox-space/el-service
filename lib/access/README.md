# Доступы к разделам

Модель: **раздел = единица доступа**. Раздел описывает одну функцию приложения
(страницу и её API). Администратор выдаёт сотруднику набор разделов; всё
остальное скрыто и на сервере, и в интерфейсе.

## Как это работает

| Слой | Где | Что делает |
|---|---|---|
| Реестр | `lib/access/registry.ts` | список разделов: название, описание, путь, роли по умолчанию |
| БД | `User.accessOverride` + `SectionAccess` | индивидуальные доступы сотрудника |
| Сервер | `lib/access/server.ts` | `getSessionAccess`, `requireSection`, `requireAnySection` |
| API | в каждом роуте | `const guard = await requireSection("violations"); if (!guard.ok) return guard.response;` |
| Меню | `components/shell/nav-config.ts` | у пункта указан `section`, меню фильтруется по доступам |
| Страница | `app/admin/layout.tsx` | раздел определяется по адресу (`sectionForPath`) и закрывается экраном «нет доступа» |
| Управление | `/admin/users` → сотрудник | матрица «Доступ к разделам» |

Правила разрешения доступа (`buildAccess`):

1. `ADMIN` — все разделы, независимо от настроек;
2. `accessOverride = true` — ровно выданный список (`SectionAccess.allowed = true`);
3. иначе — `defaultRoles` раздела из реестра.

## Добавить доступ к новой функции

1. **Реестр** — добавьте объект в `ACCESS_SECTIONS`:

```ts
{
  id: "dutySchedule",
  label: "График дежурств",
  description: "Кто дежурит по дням, замена дежурных",
  group: "analytics",
  href: "/admin/duty",
  defaultRoles: ["ADMIN", "HEAD_TEACHER"],
}
```

2. **API** — в роутах функции:

```ts
const guard = await requireSection("dutySchedule");
if (!guard.ok) return guard.response;
```

Если раздел доступен нескольким (например, ещё и учителю) —
`requireAnySection(["dutySchedule", "workspace"])`.

3. **Навигация** — в `nav-config.ts` у пункта меню: `section: "dutySchedule"`.

Готово: раздел появится в матрице доступов, в фильтрации меню, а страница
`/admin/duty` автоматически закроется для тех, кому он не выдан — отдельный
код на странице не нужен.

## Важные детали

- Разделы с `adminOnly: true` (сейчас «Персонал») нельзя выдать: они не показываются
  в матрице и отфильтровываются на сервере.
- Свои доступы администратор менять не может (защита от потери управления).
- Если у сотрудника нет ни одного доступного админского раздела, меню не покажет
  пустых групп; на главной ему будет доступен только рабочий экран.
- Изменения доступов применяются после перезагрузки страницы: `AccessProvider`
  читает `/api/access/me` при монтировании.

# Рецепт 1. Новая роль

Роль — это про «кто человек» (учитель, завуч, охрана). Разделы — про «что он видит».
Доступ по умолчанию = объединение доступов всех ролей сотрудника.

## Способ 1 (основной): через интерфейс

`/admin` → **Администрирование → Роли и доступы**:

1. «Добавить роль»;
2. название латиницей (`METHODIST`, `CURATOR`), описание для админа;
3. отметить разделы, которые роль открывает по умолчанию;
4. «Создать роль».

Роль сразу доступна в карточке сотрудника («Роли и права»). Доступы сотрудника
пересчитываются на сервере при каждом запросе — повторный вход не нужен,
достаточно обновить страницу.

Изменить доступы роли можно там же («Изменить доступы»): они применятся ко всем
сотрудникам с этой ролью, у которых не включены индивидуальные доступы.
Роль, выданную сотрудникам, удалить нельзя — сначала её нужно снять.

### Где это хранится

| Что | Где |
|---|---|
| Название и описание | таблица `Role` |
| Доступы роли по умолчанию | `Role.defaultSections` (массив id разделов) |
| Подпись в интерфейсе | `lib/roles.ts` → `ROLE_META` (необязательно) |

Если `defaultSections` пуст, берутся значения из реестра
(`lib/access/registry.ts` → `defaultRoles`). Так работают встроенные роли,
и поэтому у них «доступы из реестра», пока админ не настроил их вручную.

## Способ 2: из скрипта (для CI, сидирования, прода)

```bash
node scripts/add-role.mjs METHODIST "Методист: отчёты и аналитика"
node scripts/add-role.mjs --list
```

Скрипт создаёт роль без доступов; дальше их можно выдать в интерфейсе
(«Изменить доступы») — или добавить имя роли в `defaultRoles` нужных разделов
реестра, если роль должна работать «из коробки» и после переустановки БД.

# Рецепт 2. Новая функция (страница + API)

Пример: добавляем «График дежурств» — страница `/admin/duty` и API
`/api/admin/duty`.

## Шаг 1. Раздел в реестре

`lib/access/registry.ts`:

```ts
{
  id: "duty",                       // уникальный id (camelCase)
  label: "График дежурств",         // как в матрице доступов
  description: "Кто дежурит по дням и кто может заменить", // для админа
  group: "students",                // группа матрицы: workspace | dashboard | students | discipline | analytics | admin
  href: "/admin/duty",              // путь страницы — по нему работает автозакрытие
  defaultRoles: ["ADMIN", "HEAD_TEACHER"],
}
```

Добавьте `"duty"` в тип `AccessSectionId` (тот же файл) — иначе TypeScript
не даст использовать id.

## Шаг 2. Защитить API

В каждом обработчике роута:

```ts
import { requireSection } from "@/lib/access/server";

export async function GET() {
  const guard = await requireSection("duty");   // 401 — нет сессии, 403 — нет раздела
  if (!guard.ok) return guard.response;

  // ... логика
}
```

Варианты:

- `requireAnySection(["duty", "workspace"])` — если функцию может открывать и учитель
  на рабочем экране;
- `requireAnySection(["duty", "students"])` — если данные нужны из портфолио ученика.

`guard.access` содержит `userId`, `isAdmin`, `sections` — можно использовать для
дополнительных проверок (например, «только свой класс»).

## Шаг 3. Пункт меню

`components/shell/nav-config.ts`:

```ts
{ id: "duty", label: "Дежурства", href: "/admin/duty", icon: CalendarDays, section: "duty" },
```

Пункт без `section` виден всем — так сделаны «На главную» и «Ещё».

## Шаг 4 (обычно ничего не нужно)

Страница `/admin/duty` закроется автоматически: `app/admin/layout.tsx`
вычисляет раздел по адресу через `sectionForPath()` и показывает «Нет доступа».
Меню отфильтруется само, матрица доступов в профиле сотрудника обновится сама.

Дополнительно править нужно только если:

- страница **вне** `/admin` (как главная `/`): добавьте проверку
  `if (!accessLoading && !can("duty")) return <NoAccess />;`
- у страницы несколько разделов — оставьте `href` у основного, остальные
  защищайте в API.

## Чек-лист перед коммитом

- [ ] id добавлен в `AccessSectionId`;
- [ ] `href` совпадает с реальным путём страницы;
- [ ] все роуты функции вызывают `requireSection` / `requireAnySection`;
- [ ] у пункта меню указан `section`;
- [ ] `defaultRoles` заполнены осознанно (или пусты — тогда только по выдаче);
- [ ] проверено под сотрудником без доступа: API отдаёт 403, страница — «Нет доступа».
