# Аудит миграции сотрудников (`scripts/migrate-teachers-full.js`)

Дата: проверка выполнена на текущей ветке `el-service-v2-test`, данные источника
запрошены вживую, состояние БД — моковая PostgreSQL на `127.0.0.1:55432`.

---

## 1. Что делает скрипт

1. **Нормализация существующих пользователей** — `normalizeExistingUsers()`:
   проходит по всем `User`, приводит email к `lower/trim`. Если такой email уже есть
   у другого пользователя — переносит `Class.ownerId`, `ClassShare`, `Attendance`,
   `Pass`, удаляет `UserRole` и **удаляет пользователя**.
2. **Загрузка списка** — `GET https://school1298.ru/portal/workers/workersPS-no.json`
   (портал школы, поле `value`). Без ретраев, таймаута и проверки схемы.
3. **Роли** — создаёт при отсутствии `TEACHER` и `CLASS_TEACHER`.
4. По каждому сотруднику:
   - валидирует email (`есть @`, не `нет`/`null`) и ФИО;
   - создаёт `User`, если email не найден; имя **не обновляет**;
   - всегда выдаёт `TEACHER`;
   - разбирает `classStr` (`"N-Б"`, несколько — через запятую), находит класс по
     имени (точное, lower, upper), создаёт при отсутствии, **перезаписывает
     `ownerId`**, если владелец другой;
   - при наличии класса выдаёт `CLASS_TEACHER`.
5. Печатает итоги в консоль. Exit code всегда 0, кроме падения Prisma.

Запуск: `node scripts/migrate-teachers-full.js` с `DATABASE_URL` в окружении.
В `package.json` и документации скрипт не зарегистрирован.

## 3. Проблемы

### Критично

**3.1. Формат класса: `1-А` vs `1А` → дубли классов и пустые классы**

Скрипт ищет класс по `name`, `name.toLowerCase()`, `name.toUpperCase()`
(`"1-А"`, `"1-а"`), но в БД лежит `"1А"`. Совпадений нет → на чистой базе
создаются **118 новых классов** `1-А…11-Т`, а существующие `1А…10А` остаются
без владельцев.

Последствия:

- `/api/classes` сопоставляет учеников по `studentsByClass.get(cls.name)` —
  у новых классов **0 учеников**, посещаемость и пропуска не работают;
- фильтры по классу в нарушениях/ВШУ/отсутствиях идут по `className` из АИС
  (`1А`) — нарушения, созданные из нового класса `1-А`, в эти фильтры не попадут;
- классный руководитель видит «пустой» класс и теряет реальный;
- параллельно в списке классов остаются старые «пустые» записи.

**3.2. Удаление «дублей» пользователей — разрушительное и неполное**

`normalizeExistingUsers()` физически удаляет аккаунт, если email отличается
только регистром. При этом:

- переносятся только `Class.ownerId`, `ClassShare`, `Attendance`, `Pass`;
- **не переносятся** `Violation.teacherId`, `SelfExit.teacherId`,
  `Authorization.teacherId`, `Note.teacherId`, `News.teacherId`,
  `SchoolRecord.registeredBy/releasedBy` — это обычные строки без FK, записи
  остаются с id удалённого пользователя (сироты);
- **не переносится `SectionAccess`** — индивидуальные доступы удаляются
  каскадом (`onDelete: Cascade`), сотрудник теряет ручную настройку разделов;
- роли «дубля» просто удаляются — если это был единственный `ADMIN`, система
  остаётся без администратора;
- нет проверки, что удаляется не текущий пользователь и не последний админ.

**3.3. Нет синхронизации: роли и владение классами не отзываются**

Скрипт только добавляет. Если сотрудник уволился, ушёл из классных или его
класс передали другому:

- `CLASS_TEACHER` остаётся навсегда;
- старый класс продолжает числиться за прежним владельцем (`ownerId` никто не
  очищает);
- при передаче класса новому учителю прежний владелец теряет класс молча, но
  роль у него остаётся.

Итог: «кто классный руководитель» в БД расходится с реальностью, и это
накапливается с каждым запуском.

### Высокий риск

**3.4. `TEACHER` выдаётся всем 285 сотрудникам с email**

В источнике — не только учителя: администрация, соцпедагог, психологи,
библиотека, охрана, бухгалтерия. Все получают `TEACHER`, а в текущей модели
доступа `TEACHER` по умолчанию даёт раздел **`myClass`** (посещаемость,
пропуска, нарушения). Дополнительно глобальная кнопка фиксации нарушений
показывается всем с `myClass`, а `ViolationModal` ищет ученика по всей школе —
то есть **не-педагог может зафиксировать нарушение любому ученику**.

**3.5. Конфликт владельцев решается «последний записал»**

`11-Т` и `7-Б` заявлены двумя учителями. Скрипт по очереди перезаписывает
`ownerId`, побеждает последний в JSON. Второй учитель тоже получает
`CLASS_TEACHER`, но класса не видит. Никакого отчёта о конфликте нет —
результат зависит от порядка записей в источнике.

**3.6. Нет транзакций и честного кода возврата**

Каждый сотрудник обрабатывается отдельными запросами. Ошибка посередине
(например, на создании класса) ловится в `catch`, пишется в консоль и
**не влияет на итог**: exit code 0. Возможны состояния «пользователь есть,
роли нет» и «роль есть, класса нет». Повторный запуск это не чинит
(роль создаётся, класс — нет).

**3.7. Порядок шагов: сначала разрушение, потом загрузка**

`normalizeExistingUsers()` вызывается до `fetchTeachers()`. Если сеть/портал
недоступны, функция вернёт `[]`, скрипт напишет «Нет данных» и завершится
успешно — **уже удалив дубли и роли**.

### Средний риск

**3.8. Имя не нормализуется**

`name` берётся как есть: у 2 сотрудников хвостовой пробел. Поиск по ФИО и
сортировка в интерфейсе будут с «невидимыми» различиями. Кроме того, имя
существующего пользователя не обновляется при смене в источнике.

**3.9. Валидация email поверхностная**

Проверяется только наличие `@`; домен не проверяется. 21 запись без email
пропускается молча — часть из них может быть реальными сотрудниками без
корпоративной почты, но отчёт не показывает, кто именно выпал.

**3.10. `parseClasses` создаёт класс с `grade = 0`**

При нестандартном значении (`1A` без дефиса, лишние символы) возвращается
`{ grade: 0, letter: "" }` и создаётся класс, который не попадёт ни в один
фильтр корпуса (1–3 / 4–6 / 7–11). Сейчас данные в порядке, но защиты нет.

**3.11. Нет `dry-run`, отчёта и резервной копии**

Запуск сразу пишет в боевую БД. Нет `--dry-run`, нет JSON/CSV-отчёта «что
изменится», нет снимка до применения. `DATABASE_URL` не проверяется на
принадлежность окружению — скрипт одинаково охотно отработает по продакшену.

**3.12. Внешний источник без контракта**

Формат `workersPS-no.json` не версионирован: поля `name`, `email`, `classStr`
могут переименовать. Таймаута, ретраев и валидации схемы нет; TLS без
специальных настроек из некоторых окружений не проходит (при аудите пришлось
отключать проверку сертификата, чтобы прочитать данные).

### Низкий риск

**3.13. Производительность и уникальность**

Нет уникального индекса на `Class.name`: два параллельных запуска создадут
дубли. Обработка последовательная, ~1000+ запросов; при 300+ сотрудниках
это минуты, но без батчей и без прогресса.

**3.14. Слабый аудит**

`assignedBy: 'migration'` — не id пользователя. Понять, кто и когда выдал
роль, нельзя.

**3.15. Легаси-скрипт `scripts/migrate-to-postgres.ts`**

Содержит ошибку: оба клиента создаются из одного `@prisma/client`
(«SQLite»-клиент указывает `file:./prisma/dev.db`, хотя генератор настроен на
PostgreSQL). Скрипт нерабочий и не используется — лучше удалить, чтобы не
вводил в заблуждение.

## 4. Рекомендации (по приоритету)

1. **Канонический формат класса.** Зафиксировать один вид (`1А`, как в АИС и
   приложении) и нормализовать вход миграции: `"1-А" → "1А"`. Добавить общий
   хелпер `normalizeClassName()` и использовать его и в миграции, и в API.
   Одноразово слить/переименовать уже созданные `N-А` в `NА`.
2. **Переписать нормализацию пользователей на merge.** Никаких удалений:
   переносить все ссылки (включая `Violation`, `SelfExit`, `Authorization`,
   `Note`, `News`, `SchoolRecord`, `SectionAccess`), объединять роли, запрещать
   операцию для `ADMIN`, если он последний.
3. **Сделать миграцию «синхронизацией»:** считать diff — кого нет в источнике,
   у кого изменился класс; отдельно отзывать `CLASS_TEACHER` и `ownerId`
   (или переводить класс в `ClassShare`), печатать список изменений.
4. **Роли по категориям.** Не выдавать `TEACHER` всем: для не-педагогов —
   `EMPLOYEE` (только главная). Категорию брать из источника (`vid`,
   `allstage`) или из явного справочника.
5. **Конфликты владельцев — в отчёт, а не «последний победил».** При двух
   учителях на класс: владелец по правилу (например, первый/помеченный), второму
   — `ClassShare`, а конфликт — в лог.
6. **Транзакция на сотрудника + ненулевой exit code при ошибках**, отчёт
   `migration-report.json` (создано/обновлено/пропущено/конфликты).
7. **`--dry-run` по умолчанию, `--apply` для записи**, снимок БД перед apply.
8. **Валидация источника**: обязательные поля, trim имени, домен email,
   таймаут/ретраи, проверка схемы, отчёт о пропущенных записях.
9. **Уникальность классов**: `@@unique([name])` (или `[grade, letter]`) плюс
   проверка перед созданием.
10. **Удалить `migrate-to-postgres.ts`** или починить, если он ещё нужен.

- 8 пользователей, 12 классов, `grade = 0` нет, сиротских `teacherId` нет
