## 1. Итог

Проект рабочий, но есть один подтверждённый функциональный баг, несколько системных проблем доступа и слабое место в синхронизации.

Самое важное:

1. **На главной учителя нарушения не загружаются вообще** — эффект загрузки привязан к вкладке «Нарушения», а блок отрисовывается на «Главной».
2. **Нет проверки владения классом на уровне API** — учитель может запросить чужой класс.
3. **Синхронизация скрывает причину ошибки** — дочерний процесс работает с `stdio: "ignore"`, поэтому виден только «код 1».
4. **Синхронизация перезакрепляет классы ручных сотрудников** и пропускает 21 запись без email.
5. Остались несогласованные даты/UTC и отсутствие индексов у часто используемых таблиц.

## 3. Критично (P0)

### 3.1. Нарушения на главной учителя не показываются

`app/my-class/page.tsx`:

- блок «Нарушения за сегодня» рендерится при `activeTab === "attendance"` (около строки 1038);
- эффект загрузки `todayViolations` содержит `if (activeTab !== "violations") return;` (около строки 401).

Итог: на главной блок всегда пустой, даже если нарушения есть. На вкладке «Нарушения» загружается другой список — `classViolations` — и там данные могут отображаться.

Это главная причина жалобы «не отображаются нарушения моих детей».

Дополнительно: главная показывает только выбранную дату, а не всю историю. Это нужно либо явно подписать, либо показывать последние N нарушений за период.

### 3.2. Нет row-level доступа к классам

Проверка раздела есть, проверки владения классом нет:

- `/api/attendance` — любой `classId`;
- `/api/passes` — любой `classId`;
- `/api/self-exit` — любой `classId`;
- `/api/authorizations` — любой `className`/`studentId`;
- `/api/violations` — любой `className`, `studentId`;
- `/api/news`, `/api/notes` — любой `classId`.

Любой сотрудник с `myClass` может читать чужой класс, подставив id. Нужен единый `canAccessClass(user, classId)` и фильтрация на сервере.

### 3.3. Ошибка синхронизации не диагностируется

`app/api/admin/sync/teachers/route.ts` запускает `scripts/sync-teachers.mjs` через:

```ts
spawn(process.execPath, args, { stdio: "ignore" })
```

Следствия:

- stderr/stdout скрипта теряются;
- при падении отчёт не создаётся;
- пользователь видит только «Скрипт синхронизации завершился с кодом 1»;
- невозможно понять, это недоступный источник, Prisma, cwd или данные.

Локальная проверка:

- `node --env-file=.env.local scripts/sync-teachers.mjs --verbose` — успешно, 306 записей;
- API `POST /api/admin/sync/teachers` dry-run — 200;
- `--apply` в изолированной схеме — успешно, 285 пользователей и 118 классов.

То есть в текущем локальном окружении код работает. Ошибка кода 1 в другом окружении, скорее всего, связана с сетью/контейнером/старым билдом. Нужно писать лог в файл и возвращать его в API.

### 3.4. Синхронизация может отобрать класс у сотрудника

Отчёт с реального источника:

- 306 записей;
- 285 новых пользователей;
- 106 новых классов в существующей БД (плюс 12 перезакреплений);
- **2 конфликта классов**: 11Т, 7Б;
- **21 запись без email** пропущена;
- 12 классов, которые были за ручными сотрудниками, переданы сотрудникам из источника: 1А, 1Б, 2А, 2Б, 3А, 4А, 5А, 6А, 7А, 8Б, 9А, 10А.

Если сотрудник был владельцем класса вручную, после `--apply` он может перестать быть владельцем. `/api/classes` вернёт ему пустой/другой список, и он не увидит детей и нарушения. Это вторая вероятная причина жалобы.

Нужно выбрать политику: `--adopt`, запрет перезакрепления ручных классов или предупреждение перед apply.

### 3.5. 21 сотрудник источника не импортируется

Синхронизация пропускает записи без email/ФИО. Это живые сотрудники, но они не попадут в приложение и не смогут войти. Нужна политика: генерировать служебный email, создавать без входа или показывать список пропущенных.

## 4. Важно (P1)

### 4.1. Preview не равен apply

Dry-run не создаёт классы в БД и не учитывает все конфликты так же, как apply. Счётчики `created/classes` могут отличаться от фактического результата. Кнопка «Проверить» не даёт точного прогноза.

### 4.2. Apply без транзакции

Пользователи, роли и классы меняются последовательно. Ошибка в середине оставит частично применённое состояние. Нужна транзакция или компенсирующий сценарий/чекпоинт.

### 4.3. Даты и UTC

Часть старых API использует `new Date(date)` без локальных границ:

- `app/api/attendance/route.ts`;
- `app/api/news/route.ts`;
- `app/api/notes/route.ts`;
- `app/api/admin/school-records/route.ts` (границы с `Z`).

Новые экраны истории/охраны уже используют `toLocalISODate`/`getDayRange`, но единого правила нет. Нужно везде использовать `lib/date.ts`.

### 4.4. Индексы и производительность

Нет индексов у:

- `Pass (classId, date)`;
- `Attendance (classId, date)`;
- `Violation (className, date, studentId)`;
- `SelfExit (classId, endDate)`;
- `SchoolRecord (className, isActive)`.

При росте данных дашборды и `my-class` начнут деградировать. `Violation` уже используется в нескольких агрегатах.

### 4.5. Строковые связи без FK

`Pass.classId`, `Attendance.classId`, `Violation.className`, `SelfExit.classId`, `SchoolRecord.className` — строки без внешних ключей. Переименование класса или удаление пользователя создаёт «сиротские» записи, и фильтры по классу перестают находить данные.

### 4.6. Истечение заявок только ленивое

`KeyRequest.expiresAt` отменяется при чтении состояния/истории. Если никто не открывает экран, заявка остаётся PENDING в БД. Для планшета это допустимо, но для отчётов нужен фоновый процесс.

## 5. UI/UX

### Хорошо

- Единый UI-кит и токены темы.
- Все модалки на десктопе открываются справа; мобильные — нижней шторкой.
- Пульт охраны — один экран, табы, внутренние скроллы.
- Иконки без подписей имеют `title`/`aria-label`.
- Исправлена чёрная рамка полей: цвет из `--color-border`.

### Проблемы

- Главная и вкладка «Нарушения» дублируют данные с разной логикой; пользователь думает, что нарушений нет.
- Фильтры сохраняются по-разному: localStorage, URL или только state.
- Много фильтров на пульте/истории; на планшете тесно.
- Четыре разных компонента истории (`HistoryPanel`, `AdminKeyHistorySheet`, `EmployeeKeyHistory`, `GuardHistoryPanel`) показывают разные наборы полей.
- Формы по-разному ведут себя при ошибке/закрытии.
- `npm run lint` не настроен: ESLint просит конфигурацию.

## 6. Дублирование и архитектура

- `lib/db.ts` — неиспользуемый дубликат Prisma-клиента (`lib/prisma.ts` — рабочий).

- `/api/attendance` и `/api/admin/attendance-data` считают посещаемость по-разному.
- `app/(dashboard)/page.tsx` и `app/page.tsx` — потенциально дублирующий корневой маршрут.

- Повторяющиеся блоки истории и фильтров по зданиям размазаны по страницам вместо одного hook/service.

## 7. Синхронизация: что проверить в вашей среде

1. Запустить в контейнере:
   `node scripts/sync-teachers.mjs --verbose --report /tmp/sync.json`
2. Проверить доступность `https://school1298.ru/portal/workers/workersPS-no.json` из контейнера.
3. Проверить cwd, наличие `scripts/sync-teachers.mjs` и сгенерированного Prisma Client.
4. Добавить stderr/stdout в `/tmp/el-service-sync.log`, возвращать хвост в API.
5. Для apply — бэкап, затем `--adopt`/`--keep-manual-classes` по выбранной политике.
6. Показывать пропущенные без email и конфликты классов, а не только счётчики.
